# Production facility manager portal

Entry point: `/facility.html`. Managers sign in through the existing staff sign-in and must have an active `FACILITY` role with `scope_id` equal to an active `facilities.facility_code`. This workspace does not use the presentation token, demo configuration or browser-stored sample patients/trips. The separate `/facility-demo.html` remains a presentation.

The server uses the validated session's facility scope, rejects conflicting facility IDs and checks every conversation reference against that facility's real bookings. Administrators and dispatchers select an active facility explicitly. Dispatch can open **Facility inbox** from its navigation and reply in the same workspace. The usual session expiry/revocation applies. Expired authorization clears rendered trip and conversation data.

Facility-specific entry links may use `/facility.html?facility=FACILITY_CODE`. The login redirect retains this facility. Manager accounts without an assigned facility, or with a scope different from the requested facility, are denied before a dashboard or trip request is loaded. The server also rejects conflicting facility IDs on the context endpoint. The manager's hidden selector is never used as authority for the active facility.

The header, footer, account controls and red Book a Ride sign use the main site's shared `platform.css` and `platform.js`. All portal Book a Ride buttons open the same native modal dialog over the current workspace. It loads the main booking app on demand with the assigned facility locked, restores keyboard focus when closed, supports Escape, and closes/clears its frame on lost authorization. Frequent-location booking opens this dialog with the destination prefilled. Checkout returns reopen the dialog for the saved booking.

## Operations

- **Trip board:** filter by **one timeframe plus one date**. The **Timeframe** select offers Day, Week, Month, Quarter and Year; the **Service Date** control shows the picked anchor date in words and opens a small **pop-up calendar** (one month, previous/next month navigation, the anchor day filled, today ringed). The pop-up is hidden — and consumes no layout space — until the control is clicked, and it closes as soon as a day is picked, on Escape, on an outside click, or when the control is clicked again. The timeframe resolves the anchor into a range on the Eastern calendar (Day = the anchor; Week = its Sunday–Saturday span; Month/Quarter/Year = the calendar period containing it), and a small line under the filter words the resolved range from → to (for example "Sun, Nov 1 → Sat, Nov 7, 2026"). The anchor starts as today (Eastern Time). The board shows a booking once when its outbound OR return date falls inside the range, ordered by trip date, trip time and reference, and paged 100 at a time. Search the loaded page and filter status as before. The client sends the resolved range as `GET /api/facility-portal/trips?from=YYYY-MM-DD&to=YYYY-MM-DD&page=N`, and `summary` is computed over the whole range. The `dates=YYYY-MM-DD,...` set mode (each entry a real calendar date, duplicates removed, the set sorted, at most 62 dates accepted, malformed values return the established 400 error; the response echoes `dates` as the sorted set and keeps `from`/`to` as its minimum/maximum envelope) and the `ranges=FROM..TO,...` mode (1–12 inclusive blocks, each `from <= to` with a span of at most 366 days) remain available as API surface only — the portal UI no longer uses either; when `dates` is present it takes precedence over `ranges`, and legacy `date` and single `from`/`to` requests keep their unchanged behavior. Includes unpaid/pending requests. Shows actual dispatch status, payment status, assigned driver/vehicle and saved schedules. MOCK/DEMO source bookings and MOCK statuses are excluded. The four metrics are computed over the full selected set; the unread badge covers the loaded page. Book a Ride uses the main booking app with the manager's facility locked by its existing booking authorization.
- **Routes:** choose a booked trip and outbound/return leg. Uses saved addresses for Google road directions, with provider attribution/warnings and an external driving-directions fallback. These are planned routes; no simulated vehicle positions or invented ETAs are displayed. The existing Maps browser key/domain restrictions apply.
- **Communications:** per-trip, persisted manager/dispatch inbox; status history is read from `trip_status_history`. Internal dispatch notes, private contact fields and history actors are not exposed. Messages are limited to 2,000 characters, stored as plain text, and retried using an idempotency UUID. Per-user read timestamps drive unread counts. Latest 100 messages and 100 activity entries are displayed. Delivery means saved to the shared portal, not SMS/email or a guaranteed immediate dispatch response. Urgent changes retain a visible coordination phone link.
- **Locations:** top 50 locations derived across all completed/delivered/billed/paid real bookings for that facility. Counts distinct booking references per normalized address, includes both pickup and destination, excludes the normalized facility address, and ranks by count then latest service date. Case and repeated whitespace are normalized; different address spellings remain separate. No seeded locations appear for an empty facility. A completed booking changes rankings on the next refresh. Choose **Book to this location** to prefill the destination in the embedded booking form.
- **Reporting:** the **Reporting** tab (second in the workspace navigation) shows graphical reports for the signed-in facility only, served by `GET /api/facility-portal/reports?from=YYYY-MM-DD&to=YYYY-MM-DD`. The endpoint resolves the facility exactly like the trip board — a manager's session scope, or the facility Nexus staff selected — accepts no facility of its own beyond that shared resolution, and rejects a conflicting facility ID with 403 before any aggregate is computed. Range validation mirrors the trips endpoint (real calendar dates, `from <= to`, span at most 366 days). The response contains **aggregates only** — no per-trip rows, passenger names or street addresses: `totals` (trips, completed, cancelled, pending, active, completion and cancellation rates, using the board's status buckets), a zero-filled per-day `daily` series, `byStatus` and `byServiceType` counts, `byDayOfWeek` (Sunday first) and `byHourOfDay` pickup patterns, `topDestinations` (top 8 destination **cities** extracted server-side from the stored destination address, so only locality labels ever leave the server; the facility's own address is excluded, as in Locations), and `leadTimeDays` (how far ahead each trip was booked, from `bookings.created_at` in Eastern Time, bucketed 0 / 1 / 2 / 3–7 / 8–14 / 15+ days). Matching mirrors the board: a booking counts once when its outbound **or** return date is in range, on its outbound date when that is in range and otherwise on its return date (with the return time), so the daily series sums to the headline total and every chart partitions the same trips; MOCK/DEMO bookings are excluded as on the board. The tab has its own timeframe control (Day / Week / Month / Quarter / Year plus an anchor date, defaulting to the current month) resolved with the shared `facility-range.js` rules. Charts are hand-rolled inline SVG built by `facility-reports.js` (no chart library): trips over time (grouped into weeks beyond a quarter) for demand growth and quiet stretches, status and service-type bars for coordination breakdowns and vehicle/crew mix, day-of-week and pickup-hour patterns for peak staffing, top destination areas for recurring-route planning, and the lead-time histogram for short-notice pressure. Headline cards show trips in range, completed, completion rate and cancellation rate. Every chart carries a text alternative (an aria-label summary plus a visually hidden data table), values are printed as text rather than conveyed by color alone, and an empty range shows a plain "no trips" state. Reporting refreshes when the tab is opened, when its range changes, when the staff facility selection changes and on the shared Refresh button; it does not join the 20-second board polling.
- **Ask Nex:** the facility page explicitly opts into the standard Nex visitor assistant before `platform.js` loads, with `side:'right'`. Its tab, welcome bubble and full-height drawer are mirrored to the right edge (the drawer keeps the standard `min(380px, 100vw - 70px)` width), with the tab and bubble set 110px below vertical center so they clear the site's fixed, vertically centered accessibility control on that edge; public pages keep the default left placement and no facility-specific answers are added. Nex closes with its X button, a click/tap outside the panel (except inside an open host-page dialog or aria-modal), or after 15 seconds without interaction inside the panel. Closing only hides the panel — conversation history, remembered estimate/route state, any in-progress estimate step and the welcome state persist in page memory, and reopening resumes at the latest message.

The portal refreshes every 20 seconds while visible, on manual Refresh and on return to the browser tab. Communication status is refreshed when that view is open; locations recalculate when opened and during visible polling. Poll failures retain the last successful data with a stale-data notice. All facility API responses use the API's existing `no-store` headers. The new workspace does not persist trip/message data to localStorage.

## Deployment

Migration `094.001_facility_portal.sql` creates messages/read state, constraints, and facility/date indexes. RLS is enabled without public access policies; direct `anon` and `authenticated` access is revoked when those roles exist. The trusted backend database connection must own these tables or have the intended server-side privileges. Netlify's existing build command runs migrations before publishing the application.

The checkout request carries a production-portal return flag, restricted to the internal `/facility.html` return page for both payment providers. It does not change charge calculations or authorize/confirm payment from a return URL. The existing webhook/payment confirmation remains authoritative.

Provision production managers using User Management with the correct facility code. The reserved Annapolis demo account remains demo-only and is not a production manager credential. No production accounts, trips, messages, payments or database settings were created during local verification.

In **Admin → User Management → Add user**, select the Facility role and choose **Assigned facility** before creating the account. The assignment is persisted in the initial account insert, including supported legacy-schema insert paths. In **Manage account**, the facility dropdown replaces the raw scope field for production facility managers. **Access requests → Approve** opens a facility selection dialog for facility requests. Approval and any primary facility-account scope update are committed in one transaction. All three server paths reject missing, unknown, or inactive facilities. Demo-only accounts retain their reserved presentation scope.

Validation: isolated PostgreSQL tests cover migration replay, facility isolation, inactive/unassigned scopes, real-trip filtering, return days, multi-range union/dedupe/pagination/summary and validation, date-set selection (matching, dedupe, 62-date cap, precedence over ranges, scope and validation), reporting aggregates (totals and rates, zero-filled daily series summing to the total, status/service/day-of-week/hour buckets, return-date counting, destination city labels with no street addresses or passenger names in the payload, lead-time buckets, cross-facility exclusion, staff selection and range validation), location ranking updates, private history-note exclusion, message validation/idempotency, shared dispatch replies and per-user reads. Browser fixtures cover desktop/mobile navigation, the timeframe + pop-up date picker (pop-up hidden on load and consuming no layout space, opening from the Service Date control, picking a day closing it and reloading the resolved from/to range, timeframe switches re-resolving the same anchor, Escape and outside-click closing without a change), the Reporting tab (charts render with text alternatives, the default month request, timeframe changes re-resolving the range, the empty-range state), booking prefill and locked facility, empty accounts, dispatch selection, map addresses/return legs/fallbacks, session-expiry clearing, and the right-side Ask Nex drawer with outside-tap and 15-second idle closing. Production deployment and live credentials are separate from these fixture checks.
