# Production facility manager portal

Entry point: `/facility.html`. Managers sign in through the existing staff sign-in and must have an active `FACILITY` role with `scope_id` equal to an active `facilities.facility_code`. This workspace does not use the presentation token, demo configuration or browser-stored sample patients/trips. The separate `/facility-demo.html` remains a presentation.

The server uses the validated session's facility scope, rejects conflicting facility IDs and checks every conversation reference against that facility's real bookings. Administrators and dispatchers select an active facility explicitly. Dispatch can open **Facility inbox** from its navigation and reply in the same workspace. The usual session expiry/revocation applies. Expired authorization clears rendered trip and conversation data.

Facility-specific entry links may use `/facility.html?facility=FACILITY_CODE`. The login redirect retains this facility. Manager accounts without an assigned facility, or with a scope different from the requested facility, are denied before a dashboard or trip request is loaded. The server also rejects conflicting facility IDs on the context endpoint. The manager's hidden selector is never used as authority for the active facility.

The header, footer, account controls and red Book a Ride sign use the main site's shared `platform.css` and `platform.js`. All portal Book a Ride buttons open the same native modal dialog over the current workspace. It loads the main booking app on demand with the assigned facility locked, restores keyboard focus when closed, supports Escape, and closes/clears its frame on lost authorization. Frequent-location booking opens this dialog with the destination prefilled. Checkout returns reopen the dialog for the saved booking.

## Operations

- **Trip board:** combine 1–12 Eastern Time timeframe blocks. Each block row is ordered **Timeframe** (Day, Week, Month, Quarter or Year), then **Service Date/s** (the block's anchor date), then a remove control; **Add timeframe** appends another block, defaulting to Day at the first block's current date. The board shows the union of all blocks: a booking appears once when its outbound OR return date falls in any block, ordered by trip date, trip time and reference, and paged 100 at a time. Search the loaded page and filter status as before. The client sends the resolved blocks as `GET /api/facility-portal/trips?ranges=FROM..TO,FROM..TO&page=N`; each pair must be real calendar dates with `from <= to` and a span of at most 366 days, and 1–12 blocks are accepted (malformed values return the established 400 error). The response echoes `ranges` as an array of `{from,to}` objects and keeps `from`/`to` as the minimum/maximum envelope. Legacy `date` and single `from`/`to` requests map to one block with unchanged behavior. Includes unpaid/pending requests. Shows actual dispatch status, payment status, assigned driver/vehicle and saved schedules. MOCK/DEMO source bookings and MOCK statuses are excluded. The four metrics are computed over the full union; the unread badge covers the loaded page. Book a Ride uses the main booking app with the manager's facility locked by its existing booking authorization.
- **Routes:** choose a booked trip and outbound/return leg. Uses saved addresses for Google road directions, with provider attribution/warnings and an external driving-directions fallback. These are planned routes; no simulated vehicle positions or invented ETAs are displayed. The existing Maps browser key/domain restrictions apply.
- **Communications:** per-trip, persisted manager/dispatch inbox; status history is read from `trip_status_history`. Internal dispatch notes, private contact fields and history actors are not exposed. Messages are limited to 2,000 characters, stored as plain text, and retried using an idempotency UUID. Per-user read timestamps drive unread counts. Latest 100 messages and 100 activity entries are displayed. Delivery means saved to the shared portal, not SMS/email or a guaranteed immediate dispatch response. Urgent changes retain a visible coordination phone link.
- **Locations:** top 50 locations derived across all completed/delivered/billed/paid real bookings for that facility. Counts distinct booking references per normalized address, includes both pickup and destination, excludes the normalized facility address, and ranks by count then latest service date. Case and repeated whitespace are normalized; different address spellings remain separate. No seeded locations appear for an empty facility. A completed booking changes rankings on the next refresh. Choose **Book to this location** to prefill the destination in the embedded booking form.
- **Ask Nex:** the facility page explicitly opts into the standard Nex visitor assistant before `platform.js` loads, with `side:'right'`. Its tab, welcome bubble and full-height drawer are mirrored to the right edge (the drawer keeps the standard `min(380px, 100vw - 70px)` width), with the tab and bubble set 110px below vertical center so they clear the site's fixed, vertically centered accessibility control on that edge; public pages keep the default left placement and no facility-specific answers are added. Nex closes with its X button, a click/tap outside the panel (except inside an open host-page dialog or aria-modal), or after 15 seconds without interaction inside the panel. Closing only hides the panel — conversation history, remembered estimate/route state, any in-progress estimate step and the welcome state persist in page memory, and reopening resumes at the latest message.

The portal refreshes every 20 seconds while visible, on manual Refresh and on return to the browser tab. Communication status is refreshed when that view is open; locations recalculate when opened and during visible polling. Poll failures retain the last successful data with a stale-data notice. All facility API responses use the API's existing `no-store` headers. The new workspace does not persist trip/message data to localStorage.

## Deployment

Migration `094.001_facility_portal.sql` creates messages/read state, constraints, and facility/date indexes. RLS is enabled without public access policies; direct `anon` and `authenticated` access is revoked when those roles exist. The trusted backend database connection must own these tables or have the intended server-side privileges. Netlify's existing build command runs migrations before publishing the application.

The checkout request carries a production-portal return flag, restricted to the internal `/facility.html` return page for both payment providers. It does not change charge calculations or authorize/confirm payment from a return URL. The existing webhook/payment confirmation remains authoritative.

Provision production managers using User Management with the correct facility code. The reserved Annapolis demo account remains demo-only and is not a production manager credential. No production accounts, trips, messages, payments or database settings were created during local verification.

In **Admin → User Management → Add user**, select the Facility role and choose **Assigned facility** before creating the account. The assignment is persisted in the initial account insert, including supported legacy-schema insert paths. In **Manage account**, the facility dropdown replaces the raw scope field for production facility managers. **Access requests → Approve** opens a facility selection dialog for facility requests. Approval and any primary facility-account scope update are committed in one transaction. All three server paths reject missing, unknown, or inactive facilities. Demo-only accounts retain their reserved presentation scope.

Validation: isolated PostgreSQL tests cover migration replay, facility isolation, inactive/unassigned scopes, real-trip filtering, return days, multi-range union/dedupe/pagination/summary and validation, location ranking updates, private history-note exclusion, message validation/idempotency, shared dispatch replies and per-user reads. Browser fixtures cover desktop/mobile navigation, multiple timeframe blocks (add/change/remove, union wording and request parameters), booking prefill and locked facility, empty accounts, dispatch selection, map addresses/return legs/fallbacks, session-expiry clearing, and the right-side Ask Nex drawer with outside-tap and 15-second idle closing. Production deployment and live credentials are separate from these fixture checks.
